# 복수 가능 장소 반영: hybrid-v5

- **작성:** 2026-11-24 KST
- **기준:** `develop`의 hybrid-v4 및 복수 장소 저장 기능 (`bfada58`)
- **최종 상태:** 관련 회귀 테스트 42개 통과, 개발 DB에서 8쌍·16쌍 오프라인 평가 완료. v5의 서비스 배포 API는 미검증.

## 다시 볼 때의 핵심 흐름

| 단계 | 관찰 | 다음 판단의 이유 |
|---|---|
| v4 문제 확인 | 첫 장소만 거리 계산에 사용해 뒤쪽 좌표를 놓침 | 여러 장소는 이동 경로가 아닌 가능한 장소이므로 최소 거리로 수정 |
| 기존 12쌍 반사실 시험 | 75개 추가 핀 조합에서 정답 순위 변화 0건, 오답 점수는 최대 0.0854 상승 관찰 | 원래 글에 복수 장소가 없으므로 별도 데이터가 필요 |
| 새 8쌍 시험 | 정답 1위 v4 14/16 → v5 16/16 | 의도한 둘째 장소 사례에서 효과를 확인했지만 작은 설계형 데이터 |
| 별도 16쌍 시험 | 정답 1위 v4 21/32 → v5 22/32, 개선 2건·악화 1건 | 오답도 가까워지는 경계 사례를 확인해 규칙 추가를 보류 |
| 회귀 검증 | 관련 테스트 42개 통과 | v5를 1차 버전으로 유지하고 실제 반환 완료 쌍으로 추후 평가 |

16쌍의 설계, 상세 점수와 한계는
[`2026-11-24-multi-location-holdout-v1.md`](2026-11-24-multi-location-holdout-v1.md)에
따로 남겼다. 위 지표는 합성 데이터의 **오프라인 후보 순위**이며 실제 서비스
정확도나 같은 물건일 확률을 나타내지 않는다.

## 문제와 결정

게시글은 순서가 있는 `locations` 배열을 저장하지만, v4 매칭은 첫 번째 장소를 복사한
`posts.latitude`·`posts.longitude`만 읽었다. 첫 장소가 텍스트만 있고 뒤 장소에
좌표가 있으면 거리 정보가 없는 것처럼 처리했다. 첫 좌표가 멀고 뒤 좌표가 가까운
경우에도 먼 거리만 점수에 반영했다.

팀 논의에서 여러 핀은 **이동 경로가 아닌 가능한 장소들**로 정의했다. 따라서 양쪽
게시글에서 좌표가 있는 장소들을 모아 모든 쌍의 거리를 계산하고 **최소 거리**를
사용하기로 했다. 별도의 건물명·층·호실 문자열 규칙은 추가하지 않았다. 기존
가중치, 색상 감점, 임베딩 입력도 유지한다. 한쪽에 유효한 좌표가 없으면 v4의
결측 위치 재정규화를 유지한다.

## 구현과 확인할 사례

`scoring.py`에서 관계 테이블의 좌표를 우선 읽고, 위치 행이 없는 구형 글은 기존
대표 좌표를 사용한다. 계산한 최소 거리가 위치 점수, 500m 이내 근거 표시,
`recommendation_items.distance_km`에 공통으로 전달된다. 기준 글과 후보 글의
순서를 바꾸어도 거리는 같다. 추천 실행의 알고리즘 버전은 `hybrid-v5`로 올려
v4 실행 기록과 구분한다. 게시글의 두 번째 이후 장소만 수정해도 `updated_at`이
갱신되므로 실행 지문에 반영된다.

통제 테스트에서 확인할 핵심 사례:

| 기준 글 장소 | 후보 글 장소 | 기대 결과 |
|---|---|---|
| 먼 핀, 가까운 핀 | 다른 먼 핀, 가까운 핀 | 두 번째 핀 쌍의 최소 거리 사용 |
| 텍스트만, 가까운 핀 | 가까운 핀 | 첫 장소에 좌표가 없어도 거리 계산 |
| 텍스트만 | 가까운 핀 | 거리 미상, v4 결측 처리 유지 |
| 관계 행 없는 구형 글의 대표 핀 | 구형 글의 대표 핀 | 기존 단일 좌표 계산 유지 |

2026-11-24에 EC2의 별도 Docker 일회성 컨테이너에서 브랜치 `20f9111`의
`backend/app`, `scripts`, `tests`, `evaluation`을 읽기 전용으로 연결했다. 개발 DB에
접속하지 않도록 `DATABASE_URL=sqlite+pysqlite:///:memory:`와 빈 `GEMINI_API_KEY`를
설정하고 다음 관련 테스트를 실행했다.

```text
test_matching_multi_location.py
test_matching_color_ranking.py
test_ranked_candidates_api.py
test_matching_api.py
test_matching_benchmark.py
20 passed, 1 warning in 3.15s
```

경고는 `passlib`이 Python 3.13에서 제거 예정인 `crypt`를 사용한다는 안내다.
테스트에는 두 번째 핀으로 바뀐 거리·근거리 근거·실행 기록과, 보조 장소만 수정했을 때
새 실행 ID가 생성되는 API 경로가 포함된다. 전체 백엔드 테스트나 실제 PostgreSQL
환경의 API 검증은 이 결과에 포함되지 않는다.

평가 스크립트에는 대표 좌표만 사용하는 v4 점수와 복수 장소의 v5 점수를 함께
출력하도록 했다. 기존 `benchmark_v1.json`은 변경하지 않는다. 이 평가셋의 글은
모두 단일 장소 또는 장소 없음이므로, 그 집합에서 v4와 v5의 순위 차이가 없더라도
복수 장소 품질을 입증하지 못한다.

## 후속 측정과 한계

### 복수 핀 반사실 실험 설계

기존 `benchmark_v1.json`과 그때 저장한 `result.json`의 텍스트·임베딩·정답표를
그대로 두고, [`location_scenarios_v1.json`](../location_scenarios_v1.json)에 정의한
추가 핀만 가상으로 적용하는 읽기 전용 실험을 준비했다. v4는 원래 대표 좌표만,
v5는 대표 좌표와 추가 핀 사이의 최소 거리를 사용한다. 시나리오는 (1) 텍스트
전용 첫 장소의 뒤쪽 핀, (2) 양쪽의 뒤쪽 핀, (3) 여러 핀이 지갑 혼동 후보에도
가까워지는 경우, (4) 오답 열쇠 글에만 가까운 추가 핀이 생기는 경우다. 마지막
두 경우는 v5가 불리해질 가능성을 의도적으로 시험한다.

`scripts.evaluate_location_scenarios`는 개발 DB를 읽거나 쓰지 않는다. 각 시나리오의
전체·방향별 Recall@1, Recall@5, MRR과 달라진 질의의 정답 순위·1위 후보를
출력하고 입력 파일 해시를 남긴다. 기존 평가셋을 가공한 **반사실 스트레스 테스트**이므로 독립
검증 결과로 해석하지 않는다.

2026-11-24 19:48 KST에 EC2의 별도 일회성 컨테이너에서 저장된 평가 결과
(`result.json`, SHA-256 `ecf6e277970e2c2031db9381ed2d0cd2ae7704e0a7abaecf541c85602152670a`)
와 기존 데이터셋을 사용해 첫 네 시나리오를 실행했다. DB를 연결하지 않았고
게시글·임베딩을 변경하지 않았다. 입력 시나리오 SHA-256은
`7dc4ce4cdad26167886be2bfbd1d645a93fdeb45fb492db4e269cc46a34a2278`이다.

| 추가 핀 상황 | v4 Recall@1 / MRR | v5 Recall@1 / MRR | 순위가 달라진 질의 |
|---|---|---|---:|
| W3 분실 글의 두 번째 핀 | 0.8333 / 0.9167 | 0.8333 / 0.9167 | 0 |
| K3 정답 양쪽의 두 번째 핀 | 0.8333 / 0.9167 | 0.8333 / 0.9167 | 0 |
| W3 분실 글에 두 곳 추가 | 0.8333 / 0.9167 | 0.8333 / 0.9167 | 0 |
| K3 기준 글과 K1 오답에 가까운 핀 | 0.8333 / 0.9167 | 0.8333 / 0.9167 | 0 |

네 시나리오 모두 Recall@5는 1.0000이었고, 양방향 지표도 각각 변하지 않았다.
이 결과는 **순위 개선도 악화도 관찰되지 않았다**는 뜻이다. 점수 변화량은 첫
보고서에 포함되지 않아 영향이 작았는지는 판단할 수 없다. 이에 동일한 입력에서
점수 변화 상위 사례를 출력하고 모든 글에 가능한 추가 핀을 하나씩 붙여 보는
체계적 검사를 다음 실행으로 추가했다. 특정 성공 사례를 고르거나 가중치를 조정하기
전에 위치 신호가 실제로 순위를 바꾸는 범위를 확인한다.

### 보조 핀 전체 조합 검사 결과

같은 저장 결과와 데이터셋을 유지하고, 24개 글 각각에 기존 대표 핀과 다른 장소
핀을 하나씩 붙여 보았다. 네 개의 장소 앵커 중 대표 핀과 같은 경우를 제외해 총
75개 사례가 되었다. 시나리오 파일 SHA-256은
`9d9740b9fb2378e4618c459243270815ffb1956293580cf307222a6c683de71a`이다.

| 비교 항목 | v4 기준 | v5 보조 핀 75개 사례 |
|---|---:|---:|
| Recall@1 | 0.8333 | 모두 0.8333 |
| Recall@5 | 1.0000 | 모두 1.0000 |
| MRR | 0.9167 | 모두 0.9167 |
| 정답 순위 또는 1위 후보가 바뀐 사례 | — | 0 |

`ranking_changed_cases`는 **정답 순위 또는 1위 후보가 달라진 사례 수**로 구현되어
있다. 따라서 오답 후보끼리의 하위 순서까지 같았다는 뜻은 아니다. 점수는 실제로
움직였다. 예를 들어 `lost:W3`에 `LIBRARY` 핀을 추가하면 22개 방향별 비교
쌍의 점수가 0.001 이상 달라졌다. 정답이 아닌 `lost:W3` → `found:E2` 점수는
0.6070에서 0.6924로 0.0854 올랐지만, 이 사례의 정답 순위와 1위는 유지됐다.

이 결과는 추가 핀이 **위치 점수를 계산하는 데 반영됨**을 보여주지만, 이 평가셋에서
추천 정확도가 향상됐다는 증거는 아니다. 오답 점수 상승도 관찰됐으므로 다중 핀이
항상 유리하다고 해석할 수도 없다. 기존 글 24개와 가까운 네 장소를 재조합한
반사실 실험이어서 실제 복수 장소 글의 분포를 대표하지 않는다.

당시 다음 판단은 위치 가중치 조정보다, 복수 장소가 처음부터 들어간 별도 정답 쌍과
혼동 후보로 양방향 순위를 비교하는 것이다. 특히 첫 장소가 텍스트만 있는 글,
양쪽의 두 번째 핀이 가까운 정답 쌍, 여러 장소 때문에 오답도 가까워지는 경우를
포함해야 한다. 이 데이터에서 v5의 개선과 악화 사례를 따로 확인한 뒤 가중치나
핀 개수 처리 변경 여부를 논의한다.

### 새 복수 장소 평가셋 설계: 실행 전

[`benchmark_multi_location_v1.json`](../benchmark_multi_location_v1.json)은 기존
24개 글을 수정하지 않고 새로 등록할 8개 정답 쌍, 16개 글을 정의한다. 각 기준
글은 반대 유형의 8개 후보와 비교하므로 양방향 총 128개 관계가 생긴다. 지갑,
USB, 열쇠, 우산에서 각각 비슷한 물건 두 쌍을 두어 위치가 가까워진 오답도
경쟁하게 했다. W1, K1, O1은 첫 핀과 다른 두 번째 가능한 장소에서 정답과
만나고, E1은 첫 장소가 텍스트만 있으며 두 번째 장소에 좌표가 있다. W2, E2,
K2, O2의 습득 글에도 두 장소를 넣어 한쪽 방향만 시험하지 않는다.

이 평가는 글·임베딩·정답 후보를 고정한 채 v4 대표 좌표 점수와 v5 최소 거리
점수를 비교한다. 두 방식의 차이는 위치 처리뿐이다. 제목·설명에는 물건 특징을
넣되 장소 문구는 주로 별도 위치 필드에 두어 좌표 신호를 관찰하기 쉽게 했다.
따라서 실제 사용자 글의 장소 서술 분포를 그대로 재현한 데이터는 아니다. 장소
좌표도 건물 측량값이 아닌 통제된 시험점이다. 지표 외에 정답 순위가 바뀐 질의,
오답이 1위로 올라온 질의, 거리 근거를 개별적으로 확인한다.

**당시 실행 전 상태:** 데이터셋과 등록·평가 코드를 준비했으며 개발 DB 등록 및 v4/v5
지표 측정은 아직 하지 않았다. 8쌍은 복수 장소 처리의 초기 비교에 쓰고,
Recall@5는 후보가 8개뿐인 점을 감안해 해석한다. 여기서 성능이 좋아져도
가중치를 확정하지 않는다. 성능이 나빠지면 여러 가능한 장소가 오답에도 가까운
사례인지 확인하고, 순위가 그대로면 기능 정합성 개선과 순위 효과를 구분해
기록한다. 어느 경우든 이 데이터에 맞춰 위치 규칙을 즉시 추가하지 않는다.

첫 단독 검증에서 `test_matching_benchmark.py`의 두 테스트는 통과했지만,
`test_matching_multi_location.py`의 네 테스트는 SQLAlchemy 모델 등록 오류로
실패했다. `Post.author`가 참조하는 `User` 모델을 해당 테스트 파일에서 불러오지
않은 상태였다. 이전의 큰 테스트 묶음에서는 다른 파일이 먼저 `User`를 불러와
이 누락이 드러나지 않았다. 테스트 파일에 명시적 import를 추가했다. 이 실패로
매칭 점수의 참·거짓은 판단할 수 없으며, 수정 후 같은 단독 명령으로 재검증한다.

EC2에서 수정 커밋 `bfcaa8d`를 읽기 전용 마운트로 실행한 단독 재검증 결과,
`test_matching_benchmark.py`와 `test_matching_multi_location.py`가 **6 passed in
0.57s**로 통과했다. 같은 파일을 사용한 등록 스크립트의 dry run은 **8 pairs,
16 posts, 128 labeled comparisons**를 확인했다. SQLite 메모리 DB와 빈 Gemini
키를 지정했으므로 이 단계에서 개발 DB 글·임베딩은 생성되지 않았다. 다음 단계는
개발 DB에 시험 글 16개를 등록하고 동일한 라벨로 v4와 v5를 읽기 전용 평가하는
것이다. 지표는 아직 측정되지 않았다.

단독 실행 시 같은 모델 등록 문제가 평가 스크립트에도 생기지 않도록
`evaluate_matching.py`에서 `User` 모델을 명시적으로 import했다. 등록 스크립트는
이미 `User`를 불러오고 있었다.

첫 개발 DB 등록 실행은 `post_locations` 관계가 없다는 PostgreSQL 오류로
중단됐다. EC2의 일회성 컨테이너에 최신 모델을 마운트했지만, 그 컨테이너가 연결한
DB에는 복수 장소 테이블 `post_locations`가 없다. 이 테이블을 만드는
`0013_post_locations`의 적용 상태와 DB의 실제 Alembic 버전은 아직 확인 전이다.
실패 지점은 첫 글의 `db.flush()`였고 `db.commit()`에 도달하지 않았다.
세션 종료 시 트랜잭션이 롤백되므로 이 실행으로 시험 글이 남았다고 볼 근거는
없다. 첫 글에서 실패해 Gemini 임베딩 생성도 시작하지 않았다. 실제 DB의
Alembic 버전과 시험 글 수를 읽기 전용으로 확인한 뒤 마이그레이션 범위를
결정해야 한다. 현재 DB가 0009라면 0013에 도달하려면 0010~0012도 적용해야
하므로 `upgrade head`를 바로 실행하지 않는다. 이후 등록 스크립트가 쓰기 전에
`post_locations` 존재를 검사하도록 선행 조건 확인을 추가했다.

이어진 읽기 전용 DB 조회에서 `alembic_version`은 **`0012_password_reset`**,
`to_regclass('post_locations')`는 `NULL`, 실패한 첫 시험 글
`03bc716e-65da-52c3-bbb3-e17e5b44b74c`의 수는 **0건**으로 확인됐다.
따라서 0010~0012는 이미 적용됐고 롤백도 DB에서 확인됐다. 다음에는
`0013_post_locations`와 `0014_post_location_limit_policy`까지만 적용하면
복수 장소 스키마가 현재 코드와 맞는다. 0013은 테이블을 만들고 기존 단일
장소값을 position 0에 이관하며, 0014는 장소 순서의 상한 제약을 제거한다.
`0015_keyword_conditions`는 이 실험과 무관하므로 적용 범위에서 제외한다.
마이그레이션 실행 결과가 확인되기 전에는 시험 글 등록을 재시도하지 않는다.

EC2에서 시험 브랜치의 Alembic 파일을 마운트해
`upgrade 0014_post_location_limit_policy`를 실행했다. 출력에는 0012에서
0013, 0014로 순서대로 갱신된 내역이 기록됐고, 별도의 `alembic current`는
**`0014_post_location_limit_policy`**를 반환했다. 이제 시험 글 등록을 재시도할
수 있다. 등록 결과와 v4/v5 순위 지표는 아직 측정 전이다.

### 복수 장소 평가셋 첫 결과

개발 DB의 새 글 16개를 기준으로 양방향 총 128개 라벨 관계를 평가했다.
라벨 파일 SHA-256은
`7866f5c22277ecec165c029627696b91f2a085c76532f751ad46d8ab699aed00`이다.
동일한 글·임베딩·후보 집합에서 대표 장소만 사용하는 v4와 모든 좌표 장소의
최소 거리를 사용하는 v5를 비교했다.

| 방향 | 방식 | Recall@1 | Recall@5 | MRR |
|---|---|---:|---:|---:|
| 전체 16질의 | v4 | 0.875 | 1.000 | 0.9375 |
| 전체 16질의 | v5 | 1.000 | 1.000 | 1.0000 |
| LOST→FOUND 8질의 | v4 | 0.875 | 1.000 | 0.9375 |
| LOST→FOUND 8질의 | v5 | 1.000 | 1.000 | 1.0000 |
| FOUND→LOST 8질의 | v4 | 0.875 | 1.000 | 0.9375 |
| FOUND→LOST 8질의 | v5 | 1.000 | 1.000 | 1.0000 |

v4에서 정답이 2위였던 `LOST K1 → FOUND K1`, `FOUND E1 → LOST E1`이
v5에서 모두 1위가 됐다. 두 사례 모두 둘째 장소가 의도적으로 중요한 글이다.
K1의 분실 글은 기숙사와 정문을 가능한 장소로 제시하고 정답 습득 글은 정문에
있다. E1의 분실 글은 첫 장소가 텍스트만 있고 두 번째 장소에 좌표가 있으며,
정답 습득 글은 그 좌표와 같은 장소다. 결과는 최소 거리 정책의 설계 가설과
일치한다. 다만 어떤 오답을 몇 점 차로 앞섰는지, 오답 점수도 얼마나 올랐는지는
상세 JSON을 확인하기 전이므로 인과 설명을 확정하지 않는다.

16개 질의 중 두 개가 바뀌었으므로 Recall@1 차이 0.125는 **두 질의의 순위
교체**를 뜻한다. Recall@5는 두 방식 모두 1.0이라 이 평가에서 구별력이 없다.
이 8쌍은 복수 장소 효과를 보기 위해 설계한 통제 데이터이며 실제 사용자 글의
대표 표본이나 독립 검증셋이 아니다. 따라서 v5의 일반적인 정확도가 100%라는
주장은 하지 않는다. 다음 판단 전에 바뀐 두 질의의 정답·오답 점수, 거리,
임베딩 점수와 나머지 질의의 오답 점수 상승을 확인한다.

### 순위 교체와 오답 점수 상세 분석

저장된 `multi_location_result.json`에서 순위가 바뀐 두 질의와 점수 상승 상위
오답을 조회했다. 아래 점수는 매칭 확률이 아닌 상대적 정렬 점수다.

| 기준 글 → 후보 | 정답 | v4 순위·점수 | v5 순위·점수 | v5 거리 |
|---|---:|---:|---:|---:|
| LOST K1 → FOUND K1 | 1 | 2위 · 0.8747 | 1위 · 0.9170 | 0 km |
| LOST K1 → FOUND K2 | 0 | 1위 · 0.8860 | 2위 · 0.8860 | 0 km |
| FOUND E1 → LOST E1 | 1 | 2위 · 0.8952 | 1위 · 0.9184 | 0 km |
| FOUND E1 → LOST E2 | 0 | 1위 · 0.9090 | 2위 · 0.9090 | 0.071 km |

K1은 정답의 추가 위치 점수로 1·2위가 뒤바뀌었고, v5에서 정답과 오답의
점수 차이는 0.0310이다. K2 오답 역시 최소 거리가 0 km이므로 **가까운 핀만으로
정답을 가린 것은 아니다**. E1은 첫 위치에 좌표가 없는 분실 글의 두 번째
좌표가 사용되면서 정답 점수가 올랐고, 오답 E2와의 차이는 0.0094로 작다.
두 질의 모두 정답의 임베딩 점수(각각 0.9462, 0.9453)가 비교 오답의 임베딩
점수(각각 0.8913, 0.9149)보다 높았다. 이 자료만으로 근접 위치 신호의
안전한 가중치 범위를 정할 수 없다.

오답 점수도 움직였다. `LOST E1 → FOUND O2`는 0.6034에서 0.6823으로,
`FOUND O2 → LOST E1`은 같은 점수 변화로 8위에서 5위로,
`FOUND O1 → LOST E1`은 0.6097에서 0.6879로 8위에서 3위로 올랐다.
모두 정답이 아닌 글이므로 다중 핀이 오답에도 근접 신호를 줄 수 있음을
보여준다. 현재는 1위 오답으로 올라온 사례가 없어 지표 하락은 없었다.

**다음 판단 제안:** 지금 점수 가중치를 수정하면 복수 장소 효과를 의도해
작성한 8쌍에 맞출 위험이 있다. v5의 기능 정합성 개선과 이 평가셋의 2건
순위 개선은 기록하고, 이후에는 작성 방식·핀 수·정답과 오답의 위치 관계가
다른 별도 평가셋을 고정해 다시 비교한다. 특히 같은 종류·비슷한 특징의
오답에 여러 핀이 있는 사례와 정답이 좌표 없이 텍스트만 있는 사례를 포함한다.
새 평가 결과가 나오기 전에는 핀 개수 감점이나 위치 가중치 조정을 하지 않는다.

후속 16쌍 평가에서는 두 방향의 Recall@1·Recall@5·MRR과 세 건의 순위 교체를
확인했다. 최소 거리 정책은 가능한 장소 중 하나가 가까우면 높은 위치 점수를
주므로, 장소가 많은 오답도 유리해질 수 있다. 실제 입력 분포에서 확인하기
전에는 서비스 정확도 향상 수치를 주장하지 않는다. 배포는 PR 검토·병합과
별도 절차다.

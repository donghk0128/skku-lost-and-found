# 서비스 이용 이벤트와 반환 정답 쌍

## 수집 원칙

- 로그인한 사용자의 의미 있는 행동만 기록한다. 앱의 서비스 화면은 로그인 후 접근할 수 있다.
- 검색어, 제목·본문·위치 검색 문구, 채팅 내용, 이메일, 연락처, IP, 기기 식별자는 이벤트 요청과 `event_logs`에 넣지 않는다.
- 이벤트가 실패해도 게시글 작성, 채팅 생성·종료, 반환 확인의 성공을 취소하지 않는다. 따라서 이벤트 수는 실제 행동의 하한일 수 있다.
- `occurred_at`은 앱에서 행동한 시각(서버 이벤트는 성공 직후 시각), `received_at`은 DB 서버가 기록을 받은 시각이다. 앱 시계 오차 때문에 두 값은 다를 수 있다.

## `event_logs` 스키마

| 필드 | 용도 |
| --- | --- |
| `id` | UUID 기본키. 앱은 이벤트 생성 시 하나 만들고 인증 갱신 재시도에서도 같은 값을 쓴다. 서버 이벤트는 종류와 업무 객체 ID에서 결정적으로 만든다. |
| `user_id` | 로그인 사용자. 탈퇴 시 이벤트 삭제. |
| `event_type` | 아래 허용된 행동 종류. |
| `occurred_at`, `received_at` | 발생·수신 시각 분리. |
| `visit_id` | 화면 방문 중에만 유지되는 임시 UUID. 영구 기기 ID가 아니다. |
| `post_id`, `source_post_id`, `candidate_post_id` | 해당 행동의 게시글 참조. 개인정보 삭제를 위해 FK 대신 UUID로 저장하고 탈퇴 처리에서 관련 행을 삭제한다. |
| `run_id`, `rank` | 추천 후보의 실행 기록·당시 순위. |
| `properties` | 서버가 허용한 화면명, 카테고리 ID, 필터 사용 여부, 작성 방식·완료 방식만 저장. 임의 본문은 허용하지 않는다. |

앱 이벤트 API는 `POST /api/v1/events`이며 인증이 필요하다. 알 수 없는 필드는 422로 거부한다. 추천 노출·클릭은 `recommendation_runs`와 `recommendation_items`의 실행·후보·순위가 일치하고 기준 게시글이 사용자 소유인지 확인한다. 같은 `id`가 재전송되면 한 행만 저장한다.

## 이벤트와 수집 지점

| 종류 | 위치·조건 |
| --- | --- |
| `screen_view` | 앱의 홈, 채팅, 내 게시글, 게시글 작성 화면 방문 1회. |
| `post_view` | 상세 화면에 게시글 데이터가 표시된 뒤 1회. |
| `post_created` | 일반 또는 AI 보조 게시글 저장 성공 후 서버. `creation_method`만 추가. |
| `search_applied`, `filter_applied` | 게시글 목록 조회 성공 후 적용 조건이 바뀌었을 때. 검색어 원문은 제외하고 사용 여부와 선택형 카테고리만 저장. |
| `recommendation_impression` | 추천 후보가 화면에서 50% 이상 500ms 이상 보였을 때, 후보별·방문별 최초 1회. 목록 데이터를 받았다는 이유만으로 노출로 세지 않는다. |
| `recommendation_click` | 추천 후보 카드를 눌렀을 때. `run_id`, 기준·후보 게시글, 순위를 포함. |
| `chat_started` | 새 채팅방 생성 성공 후 서버. 기존 방 재접속은 동일 방 ID로 중복되지 않는다. |
| `post_completed` | 게시글 주인이 직접 완료한 경우 서버. 반환 쌍을 추정하지 않는다. |
| `return_completed` | 채팅에서 반환 완료한 경우 서버. 쌍 없는 반환도 포함. |
| `match_confirmed` | 양쪽 사용자가 게시글 쌍을 확인한 경우 서버. |

기존 `recommendation_runs`는 입력 지문이 같으면 `run_id`를 재사용하지만 요청마다 추천 점수·순위는 다시 계산한다. 이 테이블을 실제 화면 노출 횟수로 해석하지 않는다. `visit_id`와 후보별 최초 노출 이벤트가 실제 노출의 단위다.

## 반환 정답 쌍

`return_pairs`는 채팅방 하나에 대해 `PENDING` 또는 `CONFIRMED` 상태를 저장한다. 채팅 참여자 중 한쪽이 상대 유형의 게시글을 선택해 제안하고, **다른 참여자**가 확인해야만 `CONFIRMED`가 된다. 후보 게시글은 채팅 요청자가 쓴 진행 중인 반대 유형 글이어야 한다. 확인 시 두 글을 완료하고 채팅방을 `RETURNED`로 닫는다. 다른 진행 중인 방은 게시글 완료 사유로 닫는다.

상대 게시글이 없거나 선택하지 않은 경우 기존의 채팅 반환 완료를 쓸 수 있다. 게시글 주인의 직접 완료도 유지된다. 이 두 경우는 `return_pairs`에 정답 쌍을 만들지 않는다. 채팅 종료나 단일 게시글 완료를 추천 평가용 정답으로 추정하지 않는다. `CONFIRMED`도 두 사용자의 신고·확인 기록이며 물리적 반환을 독립적으로 검증한 증거는 아니다. 따라서 추천 `Recall@K`를 계산할 때는 확인된 쌍만 레이블로 사용하고, 레이블 누락 편향을 함께 보고해야 한다.

## 운영 및 한계

- 이 변경은 마이그레이션 파일만 추가한다. 운영 DB 적용, 배포, 분석 적재는 별도 단계다.
- 이벤트 저장은 원래 업무 트랜잭션이 커밋된 뒤 별도로 시도한다. 저장 실패가 본 기능을 막지 않지만 유실 이벤트를 자동 재처리하지는 않는다.
- 앱 이벤트는 네트워크 실패 시 조용히 유실될 수 있다. 인증 토큰 갱신으로 같은 요청을 재시도하는 경우만 같은 이벤트 ID를 유지한다.
- 보관 기간과 BigQuery 적재 후 정리 정책은 분석 파이프라인 도입 시 확정한다. 그 전에는 운영 DB에 자동 삭제 작업을 추가하지 않는다.
- 회원 탈퇴 시 본인의 이벤트와 본인 게시글을 참조하는 이벤트·정답 쌍을 삭제한다.
